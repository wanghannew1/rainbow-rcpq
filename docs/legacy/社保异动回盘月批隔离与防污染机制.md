## 0. 一句话结论

**TC9W（正式异动记录）按"月+户头+区划"分批，行一经回盘办结（ATC9W8='4'）即封版；后续月份的校验/提交对它既"看不见"（每条 SQL 物理带月份条件）也"没能力写"（提交过程对 TC9W 无任何写语句）。跨月真正共享的只有 TC90 员工档案，靠单向状态字段和 CASE 护栏兜底。**

## 3. 四层防污染机制

### 层 1｜结构性隔离：提交过程对 TC9W 没有写能力

`PRC_社保异动回盘提交`（:1702-1865）内全部 TC9W 访问点只有一处：

```sql
-- :1717 停保处理——只读
FOR R_TB IN (SELECT * FROM TC9W
              WHERE ATC9W1 = '3'            -- 报减(停保)
                AND AAA030 = PRM_AAA030
                AND AAA100 = PRM_AAA020
                AND AAE002 = PRM_AAE002) LOOP
```

全包的 `INSERT INTO TC9W` 共 9 处（:966/:1009/:1139/:1164/:1232/:1275/:1308/:1369/:1469），**全部在报盘生成侧**（PRC_社保增减赋值，由 PRC_社保人员增减 调用，:470/:866），且都在校验(:1544)、提交(:1702)之前。
→ 11 月的提交"没动 TC9W"不是运气，是**该过程没有写 TC9W 的语句可执行**。

### 层 2｜物理隔离：每条 SQL 都带 月+户头+区划 三键

所有跨表语句的 WHERE 形如 `AAE002=当月 AND AAA030=户头 AND AAA100=区划`。以校验里唯一一处 TC9W 更新为例（:1592-1598）：

```sql
UPDATE TC9W SET ATC9W8 = '4'
 WHERE ATC9W8 = '1'
   AND AAA100 = PRM_AAA020      -- 区划
   AND AAA030 = PRM_AAA030      -- 户头
   AND AAE002 = PRM_AAE002;     -- 月
```

11 月提交传入 PRM_AAE002='202611'，**10 月的行在 SQL 谓词层面就不在结果集里**——隔离不依赖应用代码"记得"过滤，是每条语句的物理属性。

### 层 3｜单向状态机 + 月份锁

```
ATC9W8: '1'(待回盘) ──校验──→ '4'(已回盘办结)      # 只进不退，全包无 '4'→x 的语句
```

报盘生成开头有一把显式锁（:903-912）：

```sql
SELECT COUNT(1) INTO N_NUM FROM TC9W
 WHERE ATC9W8 = '4' AND AAA100=... AND AAA030=... AND AAE002=当月;
IF N_NUM > 0 THEN
   PRM_MSG := '当月数据已经回盘，不能重新生成，请点击查询查看历史数据';
   RETURN;   -- 整个生成被拒绝
END IF;
```

同月重生成前还会先清草稿（:917-921，仅删 `ATC9W8='1'` 的未回盘行）——办结行('4')永不复用。

### 层 4｜档案护栏（TC90 是唯一跨月共享状态）

提交的"参保成功"分支（:1743-1811，扫 `ACE10A='3' AND AAA90W='1'` 的暂存行）：

```sql
UPDATE TC90
   SET AAA203 = TO_CHAR(TO_DATE(R_CB.ABP001,'yyyy-mm-dd'),'yyyymm'),  -- 参保年月：无条件覆盖 ⚠
       AAA208 = CASE WHEN ATC90P IS NULL OR ATC90P='2'
                     THEN PRM_AAE002 ELSE AAA208 END,                  -- 起缴月：仅在保外才写 ✔
       ATC90P = '0',                                                   -- 在保
       AAA001 = R_CB.AAA001,                                           -- 个人编号：无条件覆盖 ⚠
       AAC008 = ...                                                    -- 户口房贷补标记：条件追加
 WHERE ATC900 = R_CB.ATC900;
```

- **AAA208/209 有护栏**：已在保（'0'）的人不会被后月批次改起缴月。实测：刘仁杰 AAA208 至今=202610（10 月批次写入），11 月提交后未变。
- **AAA203/AAA001 无护栏** ⚠：后月批次报盘文件里填了别的日期/编号就会覆盖档案（详见 §7）。
- 异议分支（:1833-1845）：`ACE10A='3' AND AAA90W='2'`（校验通过但申报结果=参保失败）→ `PRC_参保异议赋值` + 档案 `ATC90P='2'`。

### 3.5 提交对 TC90 档案的回写全图（三分支）

提交过程的三个分支、驱动源与档案动作（字段语义见下表）：

| 分支 | 驱动源（谁被处理） | 档案动作 | 跳过条件 |
|---|---|---|---|
| ① 停保（:1717-1742） | **TC9W** 里 `ATC9W1='3'`（报减）的本月本户头区划行——**这就是提交要"读 TC9W"的原因：报减名单在正式表，不在暂存** | `ATC90P='1'`（停保）；AAA204/AAA209 仅当原状态 '0'（在保）时才盖当月戳 | TC06 特殊情况（`ATC062 IN('1','2')` 且期间覆盖当月）→ **整人跳过不置停保** |
| ② 参保成功（:1743-1811） | TC9W_BP 里 `ACE10A='3' AND AAA90W='1'` | `ATC90P='0'`；AAA203=文件参保年月（无条件）；AAA208 仅原状态 NULL/'2' 时盖当月戳；AAA001=个人编号（无条件）；AAC008 条件追加 | 档案查不到 ATC900 → 整个提交 `-1` 终止（'【姓名】新参保更新出错'）；SQL 影响 0 行同样终止 |
| ③ 异议（:1833-1848） | TC9W_BP 里 `ACE10A='3' AND AAA90W='2'` | `PRC_参保异议赋值` + `ATC90P='2'`、AAA208=当月 | 赋值过程报错即终止提交 |

停保分支原文（:1731-1741）：

```sql
SELECT COUNT(1) INTO N_NUM FROM TC06
 WHERE AAE100 = '1' AND ATC062 IN ('1','2')
   AND (AAE002 = PRM_AAE002 OR (AAE002 <= PRM_AAE002 AND ATC06A >= PRM_AAE002))
   AND AAC001 = R_TC90.AAC001;
IF N_NUM = 0 THEN      -- 无特殊情况才置停保
  UPDATE TC90
     SET AAA204 = CASE WHEN ATC90P='0' THEN PRM_AAE002 ELSE TO_CHAR(AAA204) END,
         AAA209 = CASE WHEN ATC90P='0' THEN PRM_AAE002 ELSE TO_CHAR(AAA209) END,
         ATC90P = '1'
   WHERE ATC900 = R_TB.ATC900;
END IF;
```

TC90 写入字段语义（按代码行为归纳）：

| 字段 | 含义 | 写入方 | 护栏 |
|---|---|---|---|
| AAA203 | 参保年月 | 分支② | ❌ 无条件覆盖（文件 ABP001 转 yyyyMM） |
| AAA208 | 参保处理月（最近一次参保生效的批次月） | 分支②③ | ✔ 仅原状态 NULL/'2' 时写 |
| AAA204/AAA209 | 停保年月/停保处理月 | 分支① | ✔ 仅原状态 '0'（在保）时写 |
| ATC90P | 参保状态：'0' 在保 / '1' 停保 / '2' 异议 | 三分支 | 状态机：0↔1、→2 |
| AAA001 | 社保个人编号 | 分支② | ❌ 无条件覆盖 |
| AAC008 | 户口性质补标记（'27' 等） | 分支② | 条件追加（AAC009 含'21'时） |
| TC90_YY.CBSIGN | 医保签约标志置 '0' | 分支②（SAFESIGN='1' 的行） | — |

三个分支全部只在**提交**时执行；导入和校验阶段 TC90 零写入。分支②③以暂存行 ace10a='3' 为前提——**校验失败的行（ace10a=2）三个分支都碰不到**，这就是张三丰1119 案例中档案零变化的原因。

## 6. 防污染机制的边界（已知问题记录 ⚠）

> **阶段归属（2026-11-19 总方针）**：第一阶段为**原样重写**——下列行为（含缺陷）须忠实复刻，不做修复；改进方案见 §6.1，归入**第二阶段升级**。

1. **档案字段无条件覆盖**：`AAA203`(参保年月)、`AAA001`(个人编号) 无护栏——后月批次文件填错即改档案。重写建议：已参保状态下禁止覆盖参保年月，或改为差异比对确认。
2. **办结月份可重导可重提**：月份锁(:903)只锁"报盘生成"，**不锁导入和提交**。张三丰1119 实际就导进了已办结的 202610；同理也可以对办结月重提，无条件覆盖 AAA203/AAA001——这是 TC90 的现实污染通道（今天刘仁杰 202611 重放只是值相同才无害）。
3. **重新导入=整月清暂存**：对话框"该月已存在数据，是否删除后重新导入？"确认后按 `月+户头+区划` 清 TC9W_BP——同月里**别人尚未提交的暂存行会被误删**（实测 202610 liy 的暂存行因此消失）。暂存行本身可弃（办结后无价值），但同月未提交批次会丢工作现场。
4. **姓名不参与匹配**：同身份证不同姓名照样通过；错位身份证命中他人也不报警。
5. **"结果列表"查 TC9W**，不查 BP/TC9W_BP05；TC9W_BP05 是 `PRC_社保补缴明细` 整月重建的派生表。排查"导入后列表为什么没有"时先分清看的是哪张表。
6. **导入对话框两视图**：`tc9w_bpStore`(`ace10a='3'` 符合) / `tc9w_bpStore_1`(`ace10a='2'` 不符合)——校验失败的行不消失，在"不符合"里看得到、ACE10B 是原因。
7. **暂存语义=整体替换**：同一(月+户头+区划)内 TC9W_BP 始终只保留最后一次确认导入的文件条目（先整月清再导），历次导入不累积、不保存历史；提交也不清暂存（行留存至下次替换）。
8. **提交不检查申报状态**：停保分支处理本月全部报减名单（TC9W `ATC9W1='3'`），**不管该名单是否已向社保局申报（ATC9W2）**——实测 2026-11-19：160 条 11-18 生成、ATC9W2='0'（未申报）的报减名单经测试提交后档案直接置 `ATC90P='1'`/`AAA209=当月`。业务上停保提前生效。重写时属已知行为，第一阶段忠实复刻。
9. **校验把整月名单宣告"已回盘"，报减可被参保回盘"捎带"办结**：校验的 `UPDATE TC9W SET ATC9W8='4' WHERE ATC9W8='1' AND 本月本户头区划` 不校验对应回盘文件是否真的导入过——只要本月发生过**任意一次**导入校验（哪怕只有 1 个参保人），整月名单（含报减）即翻为'4'；随后提交的停保分支又只按 `ATC9W1='3'` 扫月、不看 ATC9W8/ATC9W2，报减即全量生效。实测：202611 唯一导入为 1 人参保，160 条未申报报减名单被"捎带"停保。根因=批次聚合键错用（月+户头+区划 而非 batch_id），属 §6.1 第二阶段根治项；第一阶段忠实复刻。

### 6.1 第二阶段改进方案（backlog，第一阶段不实施）

- TC9W_BP → `import_batch`（批次+文件原件+上传人，不可变）+ `import_row`（原始行+校验结果，只追加）：保留全部导入流水帐，废除"整月替换"语义，删除/校验/提交一律以 **batch_id** 为聚合键（框架现有 ACE100/BAZ002 即批次身份，legacy 弃用了它们而改用月+户头+区划反推——根因所在）。
- 校验逻辑移应用层，集合匹配下推 SQL（按 batch_id 批量）；"符合/不符合"预览读 import_row。
- 档案护栏：已参保状态禁止覆盖 AAA203/AAA001；回盘匹配补姓名比对。
- "先看后碰"交互保留：解析+校验完成后用户确认，才触碰正式表。
