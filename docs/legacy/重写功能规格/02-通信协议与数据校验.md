## 一、通信协议(spec 级)

### 请求
```
POST /ria_pojo.do?method=action
Content-Type: text/plain
Header: ajaxRequest:true, digest:sha1(escape(body).toLowerCase())
Body: DC JSON(见 00 卷形状律)
```

### digest 算法(必须精确实现)
```
digest = SHA1( escape(body_string).toLowerCase().getBytes() )
```
- escape: 仅 ASCII 字母数字+`@*_+-./` 不转义; 其余→`%XX`(≤255)/`%uXXXX`(>255)
- **勿用任何语言的内置 isalnum**(Unicode 语义陷阱)
- 服务端对 body 逐字节验证, 不匹配 → "传输的数据被篡改"

### 响应
```json
{
  "header": {"ajaxRequest": true},
  "body": {
    "parameters": {..., "appCode": "1"/"-1", "errMsg": "", "para": ""},
    "dataStores": {...}
  }
}
```

### 错误分级
| HTTP | body | 含义 | 来源层 |
|---|---|---|---|
| 200 | appCode=1 | 成功 | 业务层 |
| 200 | appCode=-1, errMsg | 业务拒绝(有 title) | 业务层 |
| 500 | HTML | :82 NPE=解析失败 或 :83=title-less 异常 | 框架层 |

## 二、数据校验规则(按层级)

### 层 1: 摘要校验(digest)
- 无条件执行(除非 header 无 digest)
- 失败 → -30022 "前台数据解析错误: 传输的数据被篡改"

### 层 2: DC 结构解析
- body JSON 解析失败 → -30022
- 空 dataStores / 空 parameters → 解析异常 → dc=null → NPE@:82

### 层 3: 交互路由
- interaction code 未注册 → "未配置交互信息"
- bean/method 不存在 → "未配置业务处理Bean"

### 层 4: 元数据校验(metadata_validate=true 的交互)
- 按 hbm 映射的 nullable=false 逐属性检查
- 错误格式: `-30050 后台校验错误` + `[字段label]数据不可为空` 或 `[字段label]数据过长`
- **一次只报一个字段**(第一个违规即中断)
- 取材规程: 解析页面 .ds.js 的 nullable=false 全集 + hbm not-null 全集, **取并集**一次到位

### 层 5: 业务校验(服务端 Java/PLSQL)
- 校验链按过程/服务内部逻辑, 拒绝消息通过 OUT 参数或 LemisException title/detail 传递
