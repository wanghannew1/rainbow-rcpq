### 2.2 「_BP 后缀」纠错：不是备份，是报盘/回盘

旧文档《数据库结构.md》把 `_BP` 解释为「BP备份 主备份表」——**错误**。官方注释与按键分析证实 `_BP` = **报盘（提交社保局/税务/公积金中心的批量文件）与回盘（对方返回文件）** 的暂存/回执表，是活跃业务表：
- `TC90_BP`=合同报盘、`TC90_BP1`=合同减少报盘、`TC90_BP3`=续签报盘、`AA97_BP`=基数调整报盘、`TC07_BP`=补退报盘、`TB97_BP01`=单位到账报盘
- `TC9W_BP*`/`TC9U_BP02` = 各险种**回盘**回执表（导入落这里，确认过程消费）

**真备份/快照表**：`*_BAK`、`*_2023`、`*_20220507`、`*_20260725`（7-25 全库快照，与主表成对：TC93/TC93_20260725、TC95_BP/TC95_BP_20260725、TJ0A1~F1 家族、TC30 等）、`*_TEMP*`、`NOT_TC90`、`ZH_*` 系列。这类约 51+ 张（清单见 `rainbow-rcpq/docs/legacy-analysis/database-migration-inventory.md` 附录 A）。

### 2.3 从未使用（零引用）

## 4. 状态触发机制（三类通道）

| 通道 | 机制 | 特点/风险 |
|---|---|---|
| **A 存储过程通道**（主通道） | 页面传 `proName` → `ProcedureService.query` → CallableStatement 调 `PKG_*.PRC_*`；appCode=-1 抛异常整体回滚 | 过半业务规则在库内 22.5 万行 PL/SQL 里 |
| **B JS save 半通道** | 前端 `setItemValue` 后 `grid.save()` → Hibernate **整行 UPDATE** | ⚠ 只发主键提交会把行内其余字段**清空**（保存必须整行） |
| **C 导入批通道** | Excel 解析 → 写 `*_BP` 暂存表 → 弹窗「提交/确认」键调存储过程消费 | 两段式；仅回盘/减免/补差线有第二步 |

### 4.1 名单表状态机（TC9W 家族 + TC9U）

```
生成报增/报减名单（通道A，PRC_各险种人员增减）
  → ATC9W8='1' 暂存, ATC9W2='0', ATC9W9=增/减, AAA90X/Y='90'(默认失败)
「已申报/未申报」键（通道B）→ ATC9W2 '0'↔'1'
[死路] 「确认可报盘」键 → PRC_各险种增减确认 ❌ 不存在 → ATC9W8='3' 全库零存在
回盘导入（通道C：Excel→TC9W_BP 暂存）→「提交」键（通道A：PRC_异动回盘提交）
「成果确认」（通道A：PRC_异动回盘校验）→ ATC9W8='4' 终态 + 回写 TC90.ATC90P/PA/PB/W + TC90_YY.CBSIGN
  ⚠ 公积金线：置4的 UPDATE 被块注释禁用 → TC9U 永远停在 '1'
「报增成功/报减成功」键（通道B）→ ATC9WF='1' + ATC9WH=当前时间
```

### 4.2 按键外的触发机制

- **调度器**：`PKG_JOB.PRC_CHECK_TC90`、`PKG_ASWB.PRC_SYN_FROM_HR_TO_WB` 直调；框架库 QRTZ_* 12 张 Quartz 表（业务上疑似已废，见 §2.3）。
- **查询隐式同步**：异议反馈/转入页「查询」先自动跑 `PRC_异议离职同步` 再 SELECT。
- **导入即终态**：税务域导入（TC30/TC31/TC93_SS）无二次确认，导入即落账。
- **TC06 闭环**：「特殊情况说明」页录入直接改变下月报增名单（生成过程的特殊变动源）。
- **外网接口**：`PKG_RCPQ_WY`/WTS_* 表（按键文档未覆盖，待梳理）。

### 4.3 死键与已确认异常（10 项精简，详见按键分析文档）

1. `PRC_公积金异动回盘校验` 置4语句被注释 → TC9U 无法终态 [包源码]
2. `PRC_社保/医保/公积金增减确认` 不存在 → 「确认可报盘」死键，'3' 全库零存在 [实测]

### 8.3 全库 33 个 INVALID 对象的真相

- **根因**：ccrcpq 的 8 个 `SYS_*` 框架视图（SYS_ORG_USER_UNIT 等）依赖 **ccrcpqu33.V_ORG_USER_UNIT / V_USER_MENU_AUTHORITY**（跨 schema 特权可见）；**每晚 02:03-02:04 备份导入按 schema 顺序展开，ccrcpq 对象先编译时框架对象未就绪** → 全库业务包被级联置 INVALID，user_errors 里的 PLS-00201/ORA-00942 是导入时刻的"假错误快照"。
- **运行时自愈**：首次调用触发懒重编译即恢复（实测：SYS_ORG_USER_UNIT 现已 VALID、可查 43 行；11-13 按键实测各过程调用全部成功即此机制）。
- **真编译失败（重编译永远过不去，调即报错）**：列漂移 5 处——`PKG_RCPQ_NEW2`(TC9U.ATC9U7 不存在)、`PKG_RCPQ_FZ_新结算`(记录组件 ATC9U2 缺失)、`PKG_RCFP_TJ`(AAEB36)、`PKG_IMP`(ATC90T1)、**`PKG_RCPQ_HM`(AA97.AAA97G ×4，2026-11-14 重放实测确认：tdbe 二级单位调转 PRC_CHANGE_EJDW 因此整机不可用)**；`PKG_IMP_FZ`(行1195 ATC9WF，前端仅异动回盘线还在引用)。前端引用核实（2026-11-14 员工管理菜单梳理）：**tdbp 合同导入已改走 PKG_派遣批量导入（10 过程全在），PKG_IMP_FZ 的 TC90_IMP 半边是死服务端代码**；仍在调用 PKG_IMP_FZ 的只有 **TC9W_HZ_IMP 系（员工异动回盘批量导入，tdck_dialog_import_bz*.js）——该线一旦使用即触发编译失败，是真故障风险**。
