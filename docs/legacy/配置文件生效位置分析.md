# 配置文件生效位置分析（WEB-INF/conf vs WEB-INF/classes）

> 结论先行：**本项目所有"系统级配置"（数据库连接、UDOLink、调度、平台框架配置）全部以 `WEB-INF/conf/` 下为准。** `WEB-INF/classes/conf/**` 下的同名副本是 Maven 资源复制产生的冗余，运行时不会被读取。
>
> 原始 Tomcat 8.0.11 包中这些配置只有 `WEB-INF/conf/` 一份，正是因为框架原生的规范位置就是 `WEB-INF/conf/`。

---

## 1. 结论摘要

| 配置文件 | 谁加载它 | 加载方式 | 生效位置 |
|---|---|---|---|
| `conf/unieap/EAPConfig.xml` | `EAPPlugin`（Struts 插件，`unieap-platform.jar`） | `ServletContext.getResourceAsStream("/WEB-INF/conf/unieap/EAPConfig.xml")`，**路径硬编码** | ✅ `WEB-INF/conf` |
| `conf/unieap/bl/lemis/ds/applicationContext-ds-baseDB.xml` | `BLConfigHandler`（EAPConfig 的 bl 组件） | `CONFIG_PATH=/WEB-INF/conf/unieap/bl` + 文件名模式，ServletContext 资源 | ✅ `WEB-INF/conf` |
| `conf/lemis/lemis-schedule.xml`、`schedule-log.xml` | `ContextLoaderListener`（web.xml） | `contextConfigLocation` 硬编码 `/WEB-INF/conf/lemis/lemis-schedule.xml` | ✅ `WEB-INF/conf` |
| `conf/unieap/udolink/conf/supportDB.properties` | `UDOLinkConfigHandler` → `SupportDBContext` → `ResourceLocator` | `OP_SYS_PATH=web_root+WEB-INF/conf/unieap/udolink/`，文件系统路径 | ✅ `WEB-INF/conf` |
| `WEB-INF/conf/unieap/cache|tc|statement|orgnization|...` 下所有组件配置 | 各 `*ConfigHandler` | EAPConfig.xml 中 `/WEB-INF/conf/...` 路径 | ✅ `WEB-INF/conf` |
| `classpath:com/neusoft/lemis/**` 等 Spring/Hibernate 配置 | Spring `classpath:` import | 类路径加载 | ✅ `WEB-INF/classes` |
| `WEB-INF/classes/conf/**`（全部） | 无任何代码引用 | 死文件 | ❌ 不生效 |

**简单说**：`WEB-INF/classes` 下生效的只有 `com/`、`menu/` 等**包路径**资源；`conf/` 这个目录下的一切都以 `WEB-INF/conf/` 为准。

---

## 2. 背景

- 原始包 `E:\apache-tomcat-8.0.11\webapps\rcpq\WEB-INF\conf\` 下只有一份配置文件；
- 从源码重新构建部署后（`E:\code\apache-tomcat-8.5.100\...`），`WEB-INF/classes\` 下**多出一份** `conf/` 目录；
- 多出的原因：`pom.xml` 将 `src/main/resources/` 整体复制到 `target/classes/`，`deploy/setup.sh` 又把 `target/classes/` 整体复制到 `WEB-INF/classes/`；
- 由于 `src/main/resources/` 下同样存在 `conf/` 目录，于是 `WEB-INF/classes/conf/**` 冗余出现。

---

## 3. 证据链（逐条核实）

### 3.1 EAPConfig.xml — 框架总配置

**加载者**：`com.neusoft.unieap.config.plugin.EAPPlugin`（`WEB-INF/lib/unieap-platform.jar`）

**字节码证据**（`javap -c`）：
```
ldc  #12  // String /WEB-INF/conf/unieap/EAPConfig.xml
...getConfig(ActionServlet, "/WEB-INF/conf/unieap/EAPConfig.xml")
```

**加载机制**：`EAPConfig` 构造器 → `ResourceTool.getInputStream(servlet, path)` = `ServletContext.getResourceAsStream(path)` → 相对 webapp 根目录解析。

**结论**：`WEB-INF/conf/unieap/EAPConfig.xml` 生效（路径写死，与 classes 副本无关）。

### 3.2 applicationContext-ds-baseDB.xml — 业务数据源

**加载者**：`com.neusoft.unieap.config.handler.BLConfigHandler`（EAPConfig.xml 中 bl 组件）

**配置来源**（`WEB-INF/conf/unieap/EAPConfig.xml`）：
```xml
<component name="bl" handler="com.neusoft.unieap.config.handler.BLConfigHandler">
    <CONFIG_PATH>/WEB-INF/conf/unieap/bl</CONFIG_PATH>
    <CONFIG_FILE>applicationContext-*.xml /lemis/ds/applicationContext*.xml ...</CONFIG_FILE>
</component>
```

**字节码证据**：`BLConfigHandler.dealNode` 将 `CONFIG_PATH`（以 `/WEB-INF/conf` 为基准）交给 `InteractionObjectFactory` → Spring `XmlWebApplicationContext`（ServletContext 资源）。

**运行日志铁证**（`src/main/resources/conf/platform.log.3`，2020-12-10 原始环境日志）：
```
Error creating bean with name 'sessionFactory' defined in
ServletContext resource [/WEB-INF/conf/unieap/bl/lemis/ds/applicationContext-ds-baseDB.xml]
```
`ServletContext resource [...]` 正是 Spring 从 webapp 根加载的日志格式。

**结论**：`WEB-INF/conf/unieap/bl/lemis/ds/applicationContext-ds-baseDB.xml` 生效。

### 3.3 lemis-schedule.xml — Quartz 调度

**加载者**：`org.springframework.web.context.ContextLoaderListener`

**配置来源**（`WEB-INF/web.xml`）：
```xml
<context-param>
    <param-name>contextConfigLocation</param-name>
    <param-value>
        /WEB-INF/conf/lemis/lemis-schedule.xml
        /WEB-INF/conf/lemis/schedule-log.xml
    </param-value>
</context-param>
```

**结论**：路径写死在 web.xml 中（`/WEB-INF/conf/...` 无 `classpath:` 前缀），`WEB-INF/conf/lemis/lemis-schedule.xml` 生效。

### 3.4 supportDB.properties — UniEAP 平台数据源

**加载链**（`WEB-INF/lib/unieap-platform-drm-3.0.jar`）：

1. `UDOLinkConfigHandler.dealNode()`（EAPConfig.xml udolink 组件）：
   ```
   OP_SYS_PATH = web_root_path.concat("WEB-INF/conf/unieap/udolink/")   // 来自 EAPConfig.xml
   → DrmSysManager.setOPSysPath(OP_SYS_PATH)
   ```
2. `DrmSysManager.start()` → `SupportDBContext`：
   ```java
   ResourceLocator.findResourceInClasspath("conf/supportDB.properties")
   ```
3. `findResourceInClasspath` 查找顺序（字节码确认）：
   1. **`getUrlByOPPath()`**：`OPSysManager.getOPSysPath() + 文件名` = `webapps/rcpq/WEB-INF/conf/unieap/udolink/conf/supportDB.properties` ← **命中即返回**
   2. classpath 兜底（找的是 `conf/supportDB.properties`，classes 下实际放的是 `conf/unieap/udolink/conf/...`，名字对不上，永远兜不到）
   3. 工作目录兜底

**结论**：`WEB-INF/conf/unieap/udolink/conf/supportDB.properties` 生效。

### 3.5 WEB-INF/classes/conf/** 为什么是死文件

全仓库检索确认：
- 所有 XML 中 `classpath:` 引用只指向 `com/neusoft/...` 等包路径（如 `classpath:com/neusoft/lemis/applicationContext.xml`）；
- **没有任何** `classpath:conf/...`、`classpath*:conf/...`、`<import resource="...conf/...">` 引用；
- 反编译源码与全部 237 个 jar 中均无 `classpath:conf` 字符串。

即：`WEB-INF/classes/conf/**` 不存在任何加载入口。

## 4. ⚠️ setup.sh 隐患（重要）

`deploy/setup.sh` 修改数据库 IP 时（第 125-128 行）：

```bash
sed -i "s|jdbc:oracle:thin:@[0-9.]*:1521|jdbc:oracle:thin:@$DB_HOST:1521|g" \
    "$DEPLOY/WEB-INF/classes/conf/unieap/bl/lemis/ds/applicationContext-ds-baseDB.xml" \
    "$DEPLOY/WEB-INF/classes/conf/lemis/lemis-schedule.xml" \
    "$DEPLOY/WEB-INF/classes/conf/unieap/udolink/conf/supportDB.properties"
```

**三个文件全部位于 `WEB-INF/classes/conf/` 下 —— 全部不生效！**

- 真正生效的 `WEB-INF/conf/` 下三份**没有被修改**；
- 后果：换数据库 IP 后"看起来改了、实际不生效"，DRM/数据源继续连旧地址（登录、菜单加载失败）；
- 当前不出问题只是因为仓库中 `WEB-INF/conf` 下三份默认值（`172.16.0.60`）恰好正确，掩盖了该缺陷。

### 相关文档错误

`README.md`「需要修改的文件」章节声称：
> "以上 3 个文件各有一份备份在 `WEB-INF/conf/` 下，Tomcat 优先加载 `WEB-INF/classes/` 下的版本。"

**该说法与事实相反**：不是"classes 优先"，而是 **classes 那份根本不加载**。

## 5. 统一方案：配置全部收归 WEB-INF/conf

框架机制本来就以 `WEB-INF/conf/` 为规范位置（与原始 Tomcat 包一致），统一方案如下：

### 方案 A（推荐，最小改动）

1. **修正 `deploy/setup.sh`**：sed 目标改为 `WEB-INF/conf` 下三份（或同时改两份，保证一致）：
   ```bash
   sed -i "s|jdbc:oracle:thin:@[0-9.]*:1521|jdbc:oracle:thin:@$DB_HOST:1521|g" \
       "$DEPLOY/WEB-INF/conf/unieap/bl/lemis/ds/applicationContext-ds-baseDB.xml" \
       "$DEPLOY/WEB-INF/conf/lemis/lemis-schedule.xml" \
       "$DEPLOY/WEB-INF/conf/unieap/udolink/conf/supportDB.properties"
   ```
2. **仓库同步**：`src/main/webapp/WEB-INF/conf/` 下的三份作为唯一权威；`src/main/resources/conf/` 下同名文件删除或与 conf 保持一致（防止将来有人误改）。
3. **修正 README** 相关描述。

### 方案 B（彻底，消除冗余）

1. `pom.xml` resources 排除 `conf/` 目录（只保留 `com/`、`menu/` 等 classpath 资源）：
   ```xml
   <resource>
       <directory>src/main/resources</directory>
       <excludes>
           <exclude>conf/**</exclude>
       </excludes>
   </resource>
   ```
2. 删除 `src/main/resources/conf/**`（或保留但明确标注"仅供归档，部署以 webapp/WEB-INF/conf 为准"）。
3. 执行方案 A 第 1、3 步。

> ⚠️ 执行方案 B 前需确认无任何代码以 classpath 形式加载 `conf/` 路径（当前检索结论：无）。

---

## 6. 验证方法

1. 修改 `WEB-INF/conf/unieap/udolink/conf/supportDB.properties` 中的 IP（故意改错），重启 Tomcat：
   - 若登录/菜单加载失败 → 证实 conf 生效（预期行为）；
2. 修改 `WEB-INF/classes/conf/...` 下同名文件（故意改错），重启：
   - 若系统无任何变化 → 证实 classes 副本不生效；
3. 观察 `$CATALINA_HOME/logs/catalina.out` 中启动日志：
   - 出现 `ServletContext resource [/WEB-INF/conf/...]` 即证明从 conf 加载。
