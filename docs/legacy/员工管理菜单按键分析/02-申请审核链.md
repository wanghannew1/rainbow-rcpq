### tdbd 风险清单
1. **'22'/'24' 审核入口不可达**（IN 硬编码）——续签审核和员工调转审核实际由谁做？'22' 疑走 tdbp 批量续签导入线；'24' 疑废弃（tdbe 直接生效）。
2. **批量审核通过静默丢 '27'**：PRC_员工终止审核_批量 内部只 `SELECT ... WHERE ATB911='23'`（人才派遣.sql:82-84），JS 却把 '23'+'27' 混送（tdbd_cont.js:219-221）→ '27' 抛 NO_DATA_FOUND 被 WHEN E_EXCEPTION 吞掉（:161-164），**页面提示成功但 '27' 单子仍挂"提交未审核"**。
3. doCbSh 的 `!= "0"` 引用比较恒真（tdbdService.java:523-538）→ 实际参保年月被写成报增年月（aaa203←aaa201_ 等四处错位）。
4. 变更审核打回后 TC90 永远停在 ATB90R='2'（doCbSh 不回状态）。
5. 单笔（doCbSh）与批量（PRC_COMFIRM_SH '21'）两套并行实现行为不一致（批量版多写 TC8G/TC9V1）。
6. **错误数据删除按钮疑似坏键**：js:376 `getSelectedRowIndexs().length =1` 赋值笔误（恒真且截断数组），js:377-378 把数组传给 getRow → 取 atc900 大概率 JS 异常；且无状态校验就物理删多表。
7. 撤销终止"过程+Java"双实现各执行一遍，易漂移。

## 链路总结

写库主力 = 前端 store 半通道（LemisBusinessMgrPoJo.query/update 直映射 hbm 实体）+ 8 个 Java 服务方法 + 14 个存储过程**混用**；同一业务（变更/终止/调转审核）同时存在 Java 与 PL/SQL 两套实现且批量/单笔行为不一致——这是本链路最大维护风险，也是重写时需要「按业务语义合并、不按代码路径翻译」的核心依据。
