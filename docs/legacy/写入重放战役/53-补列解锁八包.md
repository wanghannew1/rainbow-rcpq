**实测证据(2026-11-26 上午, 同步夜后):**
- 本卷 175 列**全部存活**: 13/13 表抽样 33/33 命中, 列类型与快照逐一吻合
  (VARCHAR2(50)/(3)), 列序号全部在表尾段(TC90_BP 第 81/82/97/107 列) — 本地 ALTER 特征
- 对象重建时间戳: user 全部 **01:43** 重建、表 **01:44**、视图 **02:01** — 全库 DROP 级重组,
  但重建用的是**本库自己的 DDL**(否则我们加的列不可能出现在新表里)
- 数据确为生产新鲜: CE10 MAX(AAE036)=2026-11-25 22:46(前晚生产活动)
- 同步后 22 个 INVALID 全为**导入顺序假象**(包体 17 个 ALTER COMPILE 翻绿; 视图 8 个
  访问即懒自愈) — 与内存⑩模型一致; 补过的列都在, 包不可能真编译失败
- 唯一永久 INVALID: PRC_R_6J/PRC_R_6J_DL — 引用第三 schema HZJNPQU33SJX(本库不存在),
  全应用零调用 = **外部部署残留孤儿**, 与本系统无关, 重写清单标死

**修正后的运维模型:**
- 同步管线 ≈ 导出本库结构 → drop user 级重建 → 按本地结构建表 → 灌生产数据(按列名映射,
  本地多出的列恒 NULL) → 重建视图/授权(先于跨 schema 授权落位 → 假 INVALID)
- **DDL 存活, 数据清零**: 补列/包修复是持久的; 会话内的**测试数据**每夜被冲掉(用户的
  "任何操作被清除"感知即此); `scripts/db/reapply_vol53.py` 从"每日必需"降级为**保险备用**
- 卷34"列漂移"根因改判: 60 的本地 schema 是**老快照供给后冻结**的旧版, 生产 schema 已
  前漂(应用演进加列)而同步不搬结构 → 60 缺列、包编译失败。**生产库对自己 schema 编译
  大概率 VALID**(此前"真生产同样 INVALID"的猜测不成立); 补列本质是把 60 追平到应用
  代码(hbm/包源码)所要求的形状
- 新增列在 60 里全 NULL 且 CE10 高活跃 → 生产同样未使用这些列(升级预备列), 重写阶段 1
  按 hbm 建模即可, 无行为差异风险
