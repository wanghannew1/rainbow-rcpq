## 附录: 同步夜后 INVALID 全量处置规程(2026-11-26 实测, 22 对象全谱)

每夜 02:00 同步 DROP 级重建全库对象(user 01:43/表 01:44/视图 02:01, 用本地 DDL, 结构改动
存活、数据被生产替换), 因**导入顺序**(跨 schema 授权/依赖对象落位滞后)产生批量假 INVALID:

| 类型 | 自愈方式 | 实测 |
|---|---|---|
| 包/包体/过程 | `ALTER ... COMPILE` 一发翻绿 | 17 包全绿 ✓ |
| 视图 | **访问一次即自愈**(SELECT COUNT(*)) | 8 视图全绿 ✓(行数正常) |
| 连坐链 | 先愈根对象再访问下游(V_CBJ←V_AB01_TB90_TB93) | ✓ |
| 永久 INVALID | 仅 PRC_R_6J/PRC_R_6J_DL: 引用本库不存在的 HZJNPQU33SJX schema, 全应用零调用 | 外部部署残留孤儿, 标死 |

**操作要点**: ① ALTER 有假失败前科(ORA-01003 族, 报错但实际成功; 对视图还可能假失败
不编译)——**SELECT 访问是唯一可靠编译触发器**, 每次都必须 user_objects 复核状态;
② user_errors 是**上次编译尝试的陈旧快照**, 里面报的缺列/缺对象可能早已不缺(V_AA97_TC9T
报 AAA972 实为陈旧), 判缺列以现查 user_tab_columns 为准; ③ 处置顺序: 包(批量 ALTER)
→ 视图(逐个访问)→ 连坐链自底向上 → 终查 INVALID 名单。

一句话: **同步夜后的 INVALID 名单=导入签名, 不是损伤**; 全部处置成本 ≈ 十几条 ALTER +
十几次 SELECT, 白天首轮访问即自然自愈(应用实际运行时无感)。
