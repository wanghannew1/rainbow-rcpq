# Oracle → MySQL/PostgreSQL 迁移盘点

> 2026-11-05 生成。数据源：备份库 `172.16.0.60:1521/orcl`（Oracle 11.1，ojdbc14 直连）schema `ccrcpq`（主业务）+ `ccrcpqu33`（UniEAP 框架）；代码侧：hbm 映射 + raw SQL + PL/SQL 源（user_source 22.5 万行）三向交叉引用。

## 1. 对象总览

|---|---:|---:|

## 2. 表分类（迁移核心决策）

| 分类 | 数量 | 处理 |
|---|---:|---|
| **① 代码引用且库中存在**（hbm 543 − 库缺 22） | 521（含 22 框架表） | **必须迁移**：hbm 实体映射见 entity-table-map.md |
| ② PL/SQL 独有引用（存储过程内部用，Java 不可见） | 23 | **必须迁移**（列表见 §6） |
| ③ hbm 映射但库中不存在 | 22 | 不迁移；多为未建的历史/框架表（含 5 个 UP_RES_* 框架表） |
| ④ **零引用候选**（Java+PL/SQL 均不碰） | 330 | **候选废弃**：其中 51 个为 `*_BAK/*_TEMP/*_2023` 类备份表；建议迁移前与业务方确认后丢弃 |

结论：**799 张表 → 约 550 张需迁移，330 张候选丢弃**（可显著降低迁移工作量）。

### ①+② 必须迁移的表清单基数

- 项目业务表：`TC*` 214、`TJ*` 91、`TB*` 39、`AA*` 35、`AC*` 11 等（完整清单 = entity-table-map.md §4 全表）
- 只读视图 82 个 `V_*`（hbm 已映射，PG/MySQL 建同名视图即可）
- PL/SQL 独有表 23 个：`CA20, DLUSER, SYS_MSG, SYS_MSG_INFO_BOX, SYS_SCHEDULE_INFO, TB90_ATB903, TC18, TC70_ATC702, TC73_ATC737, TC7B_ATC7B6, TC7G_ATC7G6, TC7Z_ATC7ZZ, TC90_RATIO, TC90_ZJBG, TC97_RECORD_ML, TEMP, TEMP_TC93, TJ015, TJ01_INCOME, TJ03, TJ0A2, TJAA82, TJDL1`

## 3. 存储过程 / 包（**迁移最大工作量所在**）

### 3.1 调用通道（三条）

1. **前端动态按名调用**（最大通道）：页面 JS 传 `proName` 参数 → `ProcedureService.query` → `ProcedureDAOUtil.executeProcedure`。静态扫出前端引用 **40+ 个过程**，集中在：
   - `PKG_RCPQ`（核心业务）、`PKG_RCPQ_FZ`（工资/结算）、`PKG_IMP`/`PKG_IMP_FZ`（批量导入）
   - `PKG_RCPQ_HM`、`PKG_RCPQ_WY`（外网）、`PKG_RCPQ_TJ`（统计）、`PKG_RCPQ_FZ_JL`
2. **调度器直调**：`PKG_JOB.PRC_CHECK_TC90`、`PKG_ASWB.PRC_SYN_FROM_HR_TO_WB`
3. **过程内部互相调用**：包间依赖需整体搬迁

### 3.2 规模与风险

- PL/SQL 源码 **225,248 行**、133 个对象；**73 个中文命名对象**（`PKG_费用结算`、`PKG_工资发放`、`PKG_保险人员增减`、`PKG_人才派遣`、`PKG_税务接口`、`PKG_RCPQ_FZ_新结算`…）——**过半业务规则在数据库里，不在 Java 里**
- 最大包：`PKG_RCPQ`(340 行声明)、`PKG_保险人员增减`(304)、`PKG_RCPQ_FZ`(259)、`PKG_人才派遣`(204)
- ⚠️ 中文标识符：MySQL/PostgreSQL 均可保留但建议**重写时改英文名 + 映射表**（见 §7）
- 现有 28 个独立过程/函数 + 42 个包，重写策略：**逐包评审**——纯计算类改写为 Kotlin 服务层；重批量数据操作类保留为 PG PL/pgSQL 或改批处理任务

## 4. 序列与主键策略（选型关键）

| hbm 主键生成器 | 实体数 | 迁移含义 |
|---|---:|---|
| `sequence`（Oracle 序列） | **373** | **PostgreSQL：原生序列，几乎零改动**；MySQL 8：无独立序列对象，需改 IDENTITY 或模拟序列表 |
| `assigned`（程序赋值） | 95 | 与数据库无关 |
| `uuid.hex` | 12 | 与数据库无关 |

ccrcpq 有 **664 个序列**（ccrcpqu33 仅 2 个）。373 个实体的主键由序列驱动，**这是 PostgreSQL 的强论据**。

## 5. Oracle 专有语法（PL/SQL 翻译工作量实测）

| 语法 | 出现次数 | PostgreSQL 对应 | MySQL 对应 |
|---|---:|---|---|
| `NVL()` | 5,407 | `COALESCE`（同义支持） | `IFNULL/COALESCE` |
| `TO_CHAR/TO_DATE` | 838/582 | `TO_CHAR/TO_DATE`（兼容） | `DATE_FORMAT/STR_TO_DATE` |
| `SYSDATE` | 696 | `CURRENT_TIMESTAMP`（或保留） | `NOW()` |
| `DECODE()` | 268 | `CASE`（PG 无 DECODE，需改写） | 无，需改写 |
| `(+)` 外连接 | 82 | `LEFT/RIGHT JOIN` | 同 |
| `CONNECT BY` 层级查询 | 73 | `WITH RECURSIVE` | 同（8.0+） |
| `ROWNUM` | 67 | `LIMIT` | `LIMIT` |

**平台行为差异提醒**：空字符串=''与 NULL 等价（Oracle 特有，PG/MySQL 区分）；未加引号标识符大写折叠（Oracle）vs 小写折叠（PG）vs 大小写敏感（Linux MySQL）；日期隐式转换规则不同——PL/SQL 22.5 万行的翻译必须配套**行为对照测试**（与重写验证管线共用）。

## 6. ccrcpqu33 框架库

UniEAP 框架 schema：`UP_*` 80（组织/用户/角色）、`BT_*` 19（BPEL/工作流）、`RT_*` 16、`DRM_*` 13（资源管理）、`SYS_*` 13、`QRTZ_*` 12（**Quartz 调度表**）、`LOG_*` 7、`UNIEAP_*` 7，共 177 表。

重写决策点：新系统重写鉴权/组织模型（不用 acegi+UP_* 表）后，**框架库大部分可整体废弃**；但 Java hbm 里 26 个 `UP_*` 实体（ Administrator/Role/Category 等 32 框架实体映射）目前仍在用——重写鉴权模块时按新设计重建，届时这 177 张表随框架一起退场。

## 7. 迁移建议（选型 + 步骤）

**选型倾向 PostgreSQL**：
1. 373 个实体用序列主键 → PG 原生支持，MySQL 需逐一改造
2. PL/SQL → PL/pgSQL 语法距离更近（NVL/TO_CHAR/DECODE 大多有等价或原生支持）
3. 中文标识符、字符集处理更规范（UTF8 原生）
4. `WITH RECURSIVE` 替代 CONNECT BY 成熟

**步骤**：
1. 保留 Oracle 备份库作为**行为验证锚点**（与重写验证管线一致）
2. 导出 §①② 清单（约 550 表 + 82 视图 + 664 序列）→ 反向工程 DDL（建议用 pgloader / ora2pg 首轮转换）
3. PL/SQL 73 个中文包 → 按业务域重命名英文 + 建立映射表（此项规格化时逐包评审）
4. 330 张零引用表 → 业务确认后丢弃，不迁移
5. 数据迁移时保持主键（序列当前值同步）
